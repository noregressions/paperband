paperband

Held together by paperband.

A Maven plugin that renders one set of Markdown files as a print-ready PDF, a browsable static site, and a slide deck.

Read the guide Quick start GitHub

What it does

Paperband is for content that has to exist twice: a guide that gets printed and also browsed, a runbook that lives on a wiki and in an onboarding pack, a migration playbook that becomes a conference talk. Writing it twice means it drifts. Paperband takes one source tree and renders it as many ways as you need.

Cards, not pages

Each Markdown file is a card. Its ## headings become named blocks, and the heading text turns into a CSS class, so a theme can style a "Watch out" section differently from an intro without you marking anything up.

Three outputs, one source

A PDF with a table of contents, cross-reference page numbers and a back-of-book index. A static site with sidebar navigation. A 16:9 deck, as PDF or as a real .pptx.

Builds like the rest of your project

It's a Maven plugin, so a book builds in the same reactor, the same phases and the same CI as everything else. Broken cross-references fail the build rather than shipping.

Quick start

Needs a JDK 21+ and Maven 3.8+. The archetype scaffolds a working book, so you can see a PDF before learning any configuration:

mvn archetype:generate \
  -DarchetypeGroupId=dev.noregressions.paperband \
  -DarchetypeArtifactId=paperband-archetype \
  -DarchetypeVersion=0.1.2 \
  -DgroupId=com.example -DartifactId=my-guide

cd my-guide
mvn package

The PDF lands in target/. To put a book in a project you already have, declare the plugin there instead:

<plugin>
    <groupId>dev.noregressions.paperband</groupId>
    <artifactId>paperband-maven-plugin</artifactId>
    <version>0.1.2</version>
    <executions>
        <execution>
            <goals><goal>build</goal></goals>
            <configuration>
                <output>${project.build.directory}/book.pdf</output>
            </configuration>
        </execution>
    </executions>
</plugin>

There's no <input> in that block on purpose. Put the book at src/main/paperband/ — paperband.yaml at its root, cards under content/ — and every goal finds it without being told:

src/main/paperband/
  paperband.yaml     ← title, theme, axes, css, vars
  content/           ← the cards, at any folder depth
  layouts/           ← optional Pebble template overrides
  styles/            ← optional css

mvn package now builds the book. Every goal also runs on its own, no execution needed:

# PDF
mvn paperband:build -Dpaperband.output=target/book.pdf

# Static site
mvn paperband:site -Dpaperband.outputDirectory=target/site

# What's in the book, without rendering it
mvn paperband:structure

The first PDF render downloads headless Chromium (~300 MB) to ~/.cache/ms-playwright/. On CI without internet, pre-cache it or point PLAYWRIGHT_BROWSERS_PATH at an existing copy — a missing Chromium fails the build, there's no fallback renderer. The site goal doesn't need it.

Goals

Four goals produce something; the rest answer questions about a book so you can check your configuration without paying for a render.

GoalWhat it does
buildRender the book to a PDF, or to a deck with <renderer>pptx</renderer>
siteRender the book to a static HTML site
renderTurn an already-generated HTML file into a PDF
publishBuild every edition declared in the book's publication: block
structureList cards, sections, axes, page budgets and the auto-picked index terms
scanShow one card's frontmatter, resolved id and block list
themesList built-in themes and any of your own
renderersList renderers and whether each one works here
blocksList the registered block renderers
pagesCheck cards against their page budgets

Every parameter has a -D property, which fills it whenever the POM leaves it unset. A value set explicitly in the plugin's <configuration> wins over the command line, so declare a value you want to override as a <properties> entry (<paperband.theme>) instead.

Beyond the basics

Diagrams

```mermaid renders in the browser. ```plantuml renders server-side when you add the optional block-plantuml module to the plugin's classpath.

Includes and fragments

{% fragment %} pulls a named anchor out of a real source file at build time, so an example in the docs can't drift from the code it quotes.

Targets and conditionals

Branch content on the output profile with where: predicates — a paragraph that belongs in the printed book but not on the web.

Axes and sections

Group cards by a categorical dimension you declare (tier, subsystem). Each value gets a PDF divider, a site landing page and a nav entry.

Watermarks

Stamp "DRAFT" or a logo across the PDF, with a screen-only variant that disappears when the page is printed.

Page budgets

Declare that a card must fit on one page. The build fails when it doesn't, which catches a runbook that quietly grew a second sheet.

Editions

A publication: block cuts the same content several ways — a full guide, a mini guide, a client edition — each with its own theme, page size and card selection, from one publish goal.
