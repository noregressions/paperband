# TOC and Index

A book can open with a printed table of contents and close with a
back-of-book index. Both carry page numbers resolved against the finished
PDF's pagination. This guide's contents page and index are generated by the
two flags below.

## Turning them on

Both are off by default and switch on in the root `paperband.yaml`:

```yaml
vars:
  toc: true      # contents page after the cover / front matter
  index: auto    # index page after the last card; `true` for frontmatter-only
```

In a POM-declared book, an empty `<toc/>` marker between the `<section>`
elements places the contents page at that position:

```xml
<sections>
  <toc/>                     <!-- contents up front... -->
  <section>...</section>
  <section>...</section>
  <!-- ...or move <toc/> between sections, or after the last one -->
</sections>
```

The page lists the whole book wherever the marker sits. At most one
`<toc/>` is allowed; a second one fails the build. `vars: { toc: true }`, in
yaml or through `<book><vars>`, places the contents page up front. The index is `<index>auto</index>`
inside `<book>`. The headings default to *Contents* and *Index*; override
them with `vars.tocTitle` and `vars.indexTitle`.

The contents page lists every divider and card in the order the PDF
assembles them, with each divider's cards indented beneath it and each entry
linking to its page. Books without dividers get a
flat list. The index is built from card frontmatter:

```yaml
---
id: install
index: [installation, chromium]
---
```

Each `index:` term (a yaml list, or one comma-separated string) points at
the page of every card that declares it, grouped under first letters and
sorted case-insensitively. A book that enables `index: true` but declares no
terms renders no index page.

## Automatic terms

`index: auto` keeps the frontmatter terms and also extracts each card's
distinctive terms from its text: terms frequent in one card and rare across
the rest of the book. Scoring is TF-IDF over stemmed, stopword-filtered tokens
(Lucene's analyzers), so *theme* and *themes* count as one term and print as
the spelling the card used. Headings weigh more than body text, and short
single-token `code` identifiers (`paperband.yaml`, `<margins>`) are kept
verbatim with a boost of their own.

Extraction is deterministic. A term appearing in more than a third of the
cards is dropped, each card gets at most five auto terms, and terms shorter
than three characters or purely numeric are excluded.

Review the picks without rendering:

```bash
mvn paperband:structure -Dpaperband.input=book
```

Each card line gains an `index:` line showing its resolved terms, as the
index page will print them. Veto a pick by name:

```yaml
vars:
  index: auto
  indexStop: [running, snippet]   # never index these
```

`indexStop` (a list or comma-separated string) suppresses auto picks only;
a term you wrote in a card's own `index:` frontmatter always stays, and a
frontmatter spelling wins over an auto-pick of the same term.

## How the page numbers work

Page numbers are not known when the HTML is written; Chromium decides
pagination when it prints the PDF. The build therefore renders twice. The
first pass renders every page number as a fixed-width placeholder, the
numbers are read back from that PDF's named destinations (the same data
`mvn paperband:pages` reports), and a second pass renders the book with the
numbers filled in. Only the text inside each placeholder changes, so
pagination does not shift between passes. The build logs the second pass:

```
[INFO] Resolved 42 page reference(s) (toc/index) in a second render pass
```

The second render runs only when at least one placeholder is present;
books without `toc`/`index` build in one pass.

## PDF bookmarks

The PDF also carries a bookmark tree, shown in a viewer's sidebar. It is on
by default:

```yaml
vars:
  pdfBookmarks: false   # opt out
```

It follows the book's structure: the contents page, every divider with its
cards nested under it, the index, and a declared back page. Labels match the
printed contents, numbering included. Each bookmark points at the same named
destination as the corresponding contents entry, and writing them needs no
extra render pass. The build logs the count:

```
[INFO] Wrote 26 PDF bookmark(s)
```

Cards are bookmarked, headings inside them are not: Chromium emits a
destination only for an id the document links to, and a card's own anchor is
the only one the book links.

## Styling

Both pages take as many sheets as they need and inherit the theme's colours.
Restyle them from the book's CSS chain or a theme via `.book-toc` and
`.book-index` — entries expose `toc-kind-divider`/`toc-kind-card` and
`toc-depth-0`/`toc-depth-1` classes, the dotted leader is `.toc-leader`, and
the index's two-column layout is a `column-count` on `.index-groups`. For a
different structure entirely, override the `_book-toc.html` or
`_book-index.html` template from `layouts/` like any other bundled template.

## Watch Out

**The contents and index are PDF-only.** The `site` goal ignores both
flags; the site has its own index page and per-card navigation.

**Bookmarks and the contents page are independent.** Bookmarks are written
for a book with no contents page, and `pdfBookmarks: false` does not affect a
printed contents page.

**A `?` in place of a page number means the anchor did not exist** in the
first pass. The build logs a warning naming it. The bundled templates only reference
anchors they just generated, so a `?` normally points at a custom template
referencing a card id that isn't in the book.

## Check

Enable `toc: true`, build, and run `mvn paperband:pages` on the PDF: the
`(contents)` row shows where the TOC landed, and the numbers printed on that
page match the report's START column, since both come from the same named
destinations.
